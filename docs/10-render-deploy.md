# ☁️ Render Deployment Guide

This guide documents the current Render setup for Global Messenger. Keep deployment changes focused: do not change application functionality just to adjust hosting configuration.

## Current services

The repository Blueprint defines:

| Service | Type | Purpose |
|---|---|---|
| `global-messenger-api` | Node web service | Fastify + Socket.IO backend |
| `global-messenger-web` | Static site | React/Vite frontend |
| `global-messenger-db` | PostgreSQL | Application database |

Current public endpoints:

```text
Web:        https://global-messanger.onrender.com
API:        https://global-messanger-backend.onrender.com
API health: https://global-messanger-backend.onrender.com/health
```

## Backend configuration

The backend is deployed as a Node service, not as a Docker service.

The Blueprint currently uses:

```text
Build:
rm -rf apps/server/dist && npm install --include=dev --include=optional && npm run db:generate && npm run build -w apps/server

Start:
npm run start -w apps/server

Health check:
/health
```

The start script resolves to the compiled server entry point:

```text
node dist/index.js
```

Render supplies the runtime `PORT`. The application must listen on the platform-provided port and bind to an externally reachable interface.

## Environment variables

The backend receives its database connection from the Render PostgreSQL service through `DATABASE_URL`.

The Blueprint also configures:

- `JWT_SECRET` — generated by Render
- `NODE_ENV=production`
- `WEB_ORIGIN` — allowed frontend origins
- `PASSWORD_RESET_WEB_ORIGIN` — password-reset frontend origins
- `UPLOAD_DIR=/tmp/global-messenger/uploads`

Do not commit production secrets to Git.

## Frontend configuration

The Render static site uses:

```text
VITE_API_URL=https://global-messanger-backend.onrender.com
```

Password-reset routes are explicitly rewritten before the SPA catch-all so the reset page is not incorrectly swallowed by `/index.html`.

## Deployment procedure

1. Push the intended code to `main`.
2. Confirm the backend source contains the required routes.
3. Build the backend locally:

```bash
npm run db:generate
npm run build -w apps/server
```

4. Confirm the compiled entry point exists:

```bash
ls -la apps/server/dist/index.js
```

5. If checking the root health route, confirm the compiled output contains it:

```bash
grep -n "app.get('/'\|global-messenger-api" apps/server/dist/index.js
```

6. Deploy the latest commit from Render.
7. Wait for the deployment to become live.
8. Verify both endpoints:

```text
GET https://global-messanger-backend.onrender.com/
GET https://global-messanger-backend.onrender.com/health
```

## Expected API responses

Root endpoint:

```json
{
  "ok": true,
  "service": "global-messenger-api",
  "health": "/health"
}
```

Health endpoint:

```json
{
  "ok": true,
  "service": "global-messenger",
  "time": "<ISO timestamp>"
}
```

## Troubleshooting

### `/health` returns 200 but `/` returns `Route GET:/ not found`

The server is running, but the deployed build is not the build that contains the root route. Check the deployed commit and rebuild `apps/server` from the current source.

### `ERR_CONNECTION_REFUSED` locally

The local API is not listening on its configured port. Start the backend separately or use the project's normal `npm run dev` workflow. This is a local-process issue, not a Render routing issue.

### Render reports the service is live but API requests fail

Check, in order:

1. Render deployment logs.
2. `/health` response.
3. `VITE_API_URL` on the frontend.
4. `DATABASE_URL` and database availability.
5. CORS/`WEB_ORIGIN` values.
6. The deployed commit SHA.

Do not modify unrelated application code until these deployment checks are complete.

## Deployment safety rules

- Do not run `git clean` to fix a Render problem.
- Do not reset or discard unrelated local work.
- Do not commit `.env` files.
- Do not replace production database URLs with `localhost` values.
- Do not add destructive database commands to the Render build.
- Keep `healthCheckPath: /health` intact.
- Deploy the intended Git commit rather than relying on an unknown local working tree.
